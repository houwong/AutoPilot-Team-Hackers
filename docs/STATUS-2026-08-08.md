## 3. What we fixed, and why it mattered

These were not cosmetic. Each one produced confident, well-formed, wrong output
without raising an error.

### The agent wrote to tickets before the human approved

Operator 3 updated the live ticket **even when it decided a human must review
it**. By the time the reviewer opened the Workbench item, production had already
changed — and rejecting could not undo it. The Supabase write now sits behind
`cond_safe_execute` and only runs on `AUTO_REMEDIATE`.

### The human decision did not complete the workflow

Approving in the Workbench recorded a decision and started a **separate** run,
while the original sat parked at `step_4_rev` forever. That is judging gate #2 —
*"that decision completes the workflow"* — and we were failing it while looking
fine.

Auto **can** be resumed from outside; the endpoint was in the form markup Auto
itself serves. Approving now submits the real form and the paused run continues.

### "Processed" did not mean "the ticket changed"

The queue derived `auto_remediated` from a notification step completing. That is
evidence the orchestrator finished a branch, not that the service desk moved. A
campaign reported ITSM-2003 as `human_approved` while Supabase still held it at
"Waiting for support" with nothing written.

`verification` is now recorded **beside** `outcome`:

- `outcome` — which path did the agent take
- `verification` — did the ticket actually change

Both are shown on Processed Tickets.

### The queue ranked on the wrong field

Candidates were ordered by the stored `Priority` column, so a `Low` ticket
already breaching SLA for a VIP sorted below a `Highest` ticket comfortably
within target. The new read-only Queue Planner now runs Operator 5 SLA evidence
and Operator 6 incident detection in parallel, then passes both outputs to a new
deterministic planning operator. The old Operator 1 is not used for v2 planning.

Live validation scanned and ranked all 372 active tickets without starting the
execution orchestrator or writing to Supabase. The preview freezes rank position,
SLA/VIP evidence, incident context, policy values and workflow-run provenance.

### Smaller ones

- A parked review no longer blocks the whole queue
- Approve no longer loops forever on a ticket with no KB article
- The AI Manager works — answers from our own records and can trigger runs
- Workbench Refresh re-reads the item you are looking at
- Runs abandoned by a restart are reclaimed instead of showing as in-flight
- The Data Manager reports real per-channel delivery, not just "the step ran"

### Section 4.1 implementation

The separate Queue Planner is implemented without modifying or delegating to
the old Operator 1. It runs the new SLA evidence workflow and Operator 6 in
parallel, delegates to the new deterministic planning operator, validates the
strict result contract, and ends without invoking diagnosis, remediation,
notifications or Supabase writes.

The Command Center selects this path only when
`QUEUE_PLANNER_MODE=supervity_v2`. `legacy` remains an explicit one-line rollback;
the application never falls back automatically after a v2 failure.

### One deliberate divergence

The plan's success criterion 8 says the queue should not label a path
`auto_remediated` unless verification succeeds. We record `verification` beside
`outcome` instead of gating the label, because `outcome` is a true fact about
what the agent did and overwriting it loses that. **This is a product call — say
if you would rather it gate.**

### Open decisions (§7) left untouched

They are product calls, not implementation. The most important — *what does
"completed" mean* — no longer needs a single answer: `outcome` and
`verification` are separate fields precisely so "automation done" and "ticket
resolved" do not collapse into one word.

## 8. Two rules while testing

**Every agent run writes to live Supabase data.** Several tickets were corrupted
during testing and restored. A guard now refuses runs against closed tickets,
but do not run arbitrary ticket keys.

**Approving or rejecting ITSM-2180 consumes the CAB demo.** It sets `CHG-0001`
away from `Pending CAB Approval`, and the ticket stops escalating — it takes the
block path instead, silently. It has been reset twice today. If you practise
that flow, reset it before the demo:

```sql
-- in Supabase: change_requests
status = 'Pending CAB Approval', approver = null   where change_id = 'CHG-0001'
```

## 9. Running it

```bash
docker compose up -d          # everything, prod frontend on :3001
cd frontend && npm run dev    # hot-reload dev frontend on :3000
```

Use **3001** for the demo — that is the production build a judge would see.
Use **3000** while developing; the Docker frontend is a production build and
needs `docker compose up -d --build frontend` for every change.

Both talk to the same backend and database, so data agrees; only code can drift.
